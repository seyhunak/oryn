# 0007: Gherkin over a closed step library

- Status: accepted
- Date: 2026-11-13 (recorded retrospectively from the code)

## Context and problem statement

Scenarios are written by people, generated by the planner and produced by the recorder. They must be readable by non-developers, reviewable before approval, and safe to run: a scenario from a model or an imported document must not be able to execute arbitrary code on a worker. What format should scenarios use?

## Decision drivers

- Readability for reviewers who approve scenarios.
- No arbitrary code execution from scenario text.
- Static validation before saving, with useful diagnostics.
- One format for the editor, the planner, the recorder and traceability tags.

## Considered options

1. Gherkin compiled against a fixed library of step patterns; unknown steps are compile errors.
2. Gherkin with user-supplied step definitions in code (Cucumber style).
3. Playwright or other test code as the scenario format.
4. A custom JSON/YAML DSL.

## Decision outcome

Option 1, [`crates/oryn-bdd`](../../crates/oryn-bdd):

- The library (`library.rs`) defines each step as a regular expression, a display phrasing, a kind (`api`, `browser`, or shared), a description and an example. It is served at `GET /api/v1/step-library` and drives editor completion.
- Compilation parses Gherkin (features, backgrounds, scenario outlines with examples, tags inherited from features), matches every step, and produces typed steps or diagnostics with line numbers and suggestions. Scenarios whose steps all match are `executable`; only executable scenarios can be approved or run.
- Scenario kind (`api`, `browser`, `mixed`) is derived from its steps and decides which workers can claim it.
- Tags such as `@REQ-1` link scenarios to requirements; `@smoke` feeds regression selection.
- The planner's AI output and recorded sessions go through the same compiler.

### Consequences

- Good: scenario text cannot run code; the worst a malicious scenario can do is drive the browser or send HTTP requests to allowed hosts.
- Good: errors appear in the editor before saving.
- Bad: anything the library does not express cannot be tested without adding a step to the library (a code change).
- Not implemented: project-level composite step definitions are stored and validated (`step_definitions`) but the compiler does not expand them.

## Pros and cons of the other options

- **Custom step code**: unlimited expressiveness, but turns every project into code that workers must execute, and model-generated code could run on workers.
- **Test code as scenarios**: familiar to developers but hard to review for non-developers and unsafe to accept from a model.
- **Custom DSL**: easy to parse, but less readable and without the existing Gherkin ecosystem and conventions.
